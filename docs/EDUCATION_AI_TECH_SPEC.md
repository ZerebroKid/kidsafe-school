| Product | Platform | Users | Primary Job |
|---|---|---|---|

| Zerebro Campus | Next.js | School principals | Generate teacher codes, approve teachers, view coverage |

- **ZKid isolated** — parent UI is not even bundled, student can't snoop or reverse-engineer.
- **ZConnect combined** — many teachers are also parents; one install for both roles.
- **Zerebro Campus + Admin on web** — table-heavy, filter-heavy UIs are simpler on the web.

## 3) Roles & Multi-Role Users

`users/{userId}` stores a `roles` array, not a single role:

```json
{
  "uid": "user_abc",
  "phone": "+91XXXXXXXXXX",
  "displayName": "Naushad",
  "roles": ["parent", "teacher"],
  "primaryRole": "parent",
  "schoolIds": ["school_001"],
  "teacherProfileIds": ["teacher_123"],
  "createdAt": 1779050000000
}
```

Allowed role strings:

```text
admin | principal | teacher | parent | child
```

On app open, **ZConnect** uses `roles`:

- 1 role → straight into that home screen.
- 2+ roles → show a **role switcher** at the top of the home screen, default to `primaryRole` (or last-used).

```text
+----------------------------+
| [ Parent ]  [ Teacher ]    |  <- role switcher
|----------------------------|
| selected role's home view  |
+----------------------------+
```

Important rules:

- A `child` role is **only** valid in **ZKid**. ZConnect refuses to load student UI even if `roles` includes `child` (defense-in-depth).
- A user can be promoted to `teacher` only via principal approval (teacher code flow, see §6.2). The teacher code is **needed only once**, at first-time signup. After approval, `users/{uid}.roles` permanently includes `'teacher'`, so every later OTP login from the **same phone number** resolves to the same Firebase UID, the same `roles[]`, and lands directly on the teacher home — no code re-entry, no waiting screen.
- A user can be promoted to `principal` only via admin verification (school invite-code flow, see §6.1). The school invite code is **needed only once**, at the principal's first-time Zerebro Campus signup. After verification, `users/{uid}.roles` permanently includes `'principal'`, so every later OTP login from the same phone number lands directly on the Campus dashboard — no code re-entry, no waiting screen.
- A user becomes a `parent` by submitting the school's `inviteCode` (shared by the principal) **once** during first-time ZConnect signup. The `joinSchoolAsParent` callable validates the code and immediately grants `roles: ['parent']` — **no principal/admin approval gate**. After this one-time entry, `users/{uid}.roles` permanently includes `'parent'`, the phone number is bound to the role, and every later OTP login skips the code prompt and lands directly on the parent home.
- A user becomes a `child` by submitting the school's `inviteCode` + grade + section (shared by the parent, who got it from the principal) **once** during first-time ZKid signup. The `joinSchool` callable validates the code, picks the matching class, and immediately grants `roles: ['child']` — **no principal/admin approval gate**. The role is sticky on the phone number the same way as parent.

**`turbo.json`**

```json
  "pipeline": {
```

**`apps/guardian/metro.config.js`** (and same shape for `apps/kids`)

```javascript
const path = require('path');
const { getDefaultConfig } = require('@react-native/metro-config');

const workspaceRoot = path.resolve(__dirname, '../..');
const projectRoot = __dirname;

const config = getDefaultConfig(projectRoot);

config.watchFolders = [workspaceRoot];
config.resolver.nodeModulesPaths = [
  path.resolve(projectRoot, 'node_modules'),
  path.resolve(workspaceRoot, 'node_modules'),

config.resolver.disableHierarchicalLookup = true;

module.exports = config;
```

This combo is the standard fix for the Metro + workspace symlink issue.

## 5) Web Apps In The Monorepo

**Zerebro Campus** and **Zerebro Admin** are Next.js 14 (App Router) web apps:

- **server actions + route handlers** for callable-style server logic
- **`shared-firebase`** package for both client SDK and admin SDK use
- **Tailwind CSS** for all web UI (utility classes in each app — no separate shared UI package)
- Hosted on **Firebase Hosting** or **Vercel** (decision pending; Vercel recommended for App Router maturity)

`apps/principal-web/` (Zerebro Campus) route map:

```text
/                            -> login (phone OTP)

/teachers/code               -> rotate teacher code
```


## 6) Onboarding Flows Per App

### 6.1 Principal — Zerebro Campus

**Manual hand-off model.** The admin creates the school + a unique `inviteCode` inside Zerebro Admin and **shares the code manually** with the principal — SMS, WhatsApp, email, or in person. There is **no automated SMS** sent by our backend; Firebase Phone Auth is still the only place we send OTPs. Keeping the hand-off manual lets the admin vet the recipient (typically a known school contact) and avoids a backend SMS provider dependency.

**One-time code, sticky role.** The principal enters the code **exactly once**, during their first-time Zerebro Campus signup. After the admin verifies them via `approvePrincipal`, `users/{uid}.roles` permanently includes `'principal'` and the principal's phone number is bound to that role. **Every subsequent login is a plain OTP login with no code prompt** — Zerebro Campus reads `roles[]` from Firestore, sees `'principal'`, and goes straight to the dashboard.

```mermaid
sequenceDiagram
  participant A as Admin
  participant AW as Zerebro Admin
  participant P as Principal
  participant W as Zerebro Campus
  participant FN as Functions
  participant FS as Firestore

  rect rgb(245, 240, 225)
    Note over A,P: First-time onboarding (one-shot)
    A->>AW: create school
    AW->>FS: schools/{id} created with auto-generated inviteCode
    A-->>P: share inviteCode MANUALLY (SMS/WhatsApp/in-person)
    P->>W: login phone OTP (users/{uid}.roles = [])
    P->>W: paste school inviteCode
    W->>FN: claimSchool(inviteCode, displayName)
    FN->>FS: schools/{schoolId}/principals/{principalId}.status="pending", userId=caller.uid
    W-->>P: "Waiting for admin verification"
    A->>AW: review pending principal request
    A->>FN: approvePrincipal(schoolId, principalId)
    FN->>FS: principals/{principalId}.status="active"
    FN->>FS: schools/{schoolId}.principalUid = userId
    FN->>FS: users/{principalUid}.roles += "principal"
    FS-->>W: onSnapshot fires -> dashboard unlocked instantly
    W->>FN: rotateTeacherCode (now Group 4.3 / §6.2 chain begins)
  end

  rect rgb(225, 240, 245)
    Note over P,FS: Every later session (no code)
    P->>W: login phone OTP
    W->>FS: read users/{uid} -> roles = ["principal"]
    W-->>P: route directly to Campus dashboard
  end
```

**Edge cases:**
- **Code regenerated between claim and approval.** The pending `principals/{principalId}` doc has `userId` + `schoolId` recorded; approval works against the doc, not the code itself. So regenerating the code mid-flight doesn't break a pending request.
- **Principal rejected.** Their `principals/{principalId}.status = 'rejected'` and `users/{uid}.roles` stays `[]`. Zerebro Campus shows the onboarding gate again on next login; the principal can request a fresh code from the admin.
- **School already has an active principal.** Each `schools/{id}` is locked to ONE `principalUid` at a time. If a second person submits the same `inviteCode` while the school already has an active principal, the callable rejects with `failed-precondition` and asks the admin to rotate the code (an explicit principal-replacement flow is out of scope for the MVP).
- **Code mistyped.** `claimSchool` returns `invalid-argument` with a friendly message; no Firestore write happens, so retries are free.

### 6.2 Teacher (Inside ZConnect)

**Manual hand-off model.** The principal generates the teacher code inside Zerebro Campus (`rotateTeacherCode` callable) and **shares it manually** with the teacher over WhatsApp, SMS, or in person. There is **no automated SMS** sent by our backend — keeping the channel manual lets the principal vet the recipient and avoids a backend dependency on SMS providers beyond Firebase Phone Auth.

**One-time code, sticky role.** The teacher enters the code **exactly once**, during their first-time ZConnect signup. After the principal approves, the teacher's `users/{uid}.roles` permanently includes `'teacher'`, and the teacher's phone number is bound to that role. **Every subsequent login is a normal OTP login with no code prompt** — ZConnect's role router reads `roles[]` from Firestore, sees `'teacher'`, and goes straight to the teacher home.

```mermaid
sequenceDiagram
  participant T as Teacher
  participant G as ZConnect
  participant FN as Functions
  participant FS as Firestore
  participant P as Zerebro Campus

  rect rgb(245, 240, 225)
    Note over T,P: First-time signup (one-shot)
    T->>G: login phone OTP (users/{uid}.roles = [])
    T->>G: pick "I am a teacher" (intent picker)
    T->>G: paste teacherCode shared by principal
    G->>FN: requestTeacherJoin(teacherCode, displayName)
    FN->>FS: schools/{schoolId}/teachers/{teacherId}.status="pending"
    G-->>T: "Waiting for principal approval"
    P->>P: see pending request in Zerebro Campus
    P->>FN: approveTeacher(teacherId)
    FN->>FS: teachers/{teacherId}.status="active"
    FN->>FS: users/{teacherUid}.roles += "teacher"
    FS-->>G: onSnapshot fires -> teacher home unlocked instantly
  end

  rect rgb(225, 240, 245)
    Note over T,FS: Every later session (no code)
    T->>G: login phone OTP
    G->>FS: read users/{uid} -> roles = ["teacher"]
    G-->>T: route directly to teacher home
  end
```

**Edge cases:**
- **Code rotated between signup and approval.** The teacher's pending `teachers/{teacherId}` doc already has `userId` + `schoolId` recorded; approval works against the doc, not the code. So rotating the code mid-flight doesn't break a pending request.
- **Teacher rejected.** Their `teachers/{teacherId}.status = 'rejected'` and `users/{uid}.roles` stays `[]`. They see the onboarding gate again on next login and can request another code from the principal.
- **Teacher who is ALSO a parent.** `approveTeacher` APPENDS `'teacher'` to existing `roles[]` instead of replacing it. So a parent-teacher ends up with `roles: ['parent', 'teacher']` and the in-app `RoleSwitcher` (P3.3) lets them flip between modes.

### 6.3 Parent (Inside ZConnect)

**Manual hand-off model.** The principal **re-shares the same school `inviteCode`** they got from the admin (§6.1) with each parent — SMS, WhatsApp, in person. There is no automated SMS from our backend; the principal hands the code to the parent the same way they hand it to teachers (§6.2).

**One-time code, sticky role, NO approval gate.** The parent enters the code **exactly once**, during their first-time ZConnect signup. The `joinSchoolAsParent` callable validates the code server-side and immediately grants `roles: ['parent']` — **there is no pending state and no principal approval step**, because the only access this grants is "I can manage my own child" (which is already gated by pairing). After the one-time entry, the phone is permanently bound to the parent role; every later OTP login skips the school-code screen and lands directly on the parent home.

```mermaid
sequenceDiagram
  participant Pr as Principal
  participant Pa as Parent
  participant G as ZConnect
  participant FN as Functions
  participant FS as Firestore

  rect rgb(245, 240, 225)
    Note over Pr,Pa: First-time signup (one-shot)
    Pr-->>Pa: share school inviteCode MANUALLY (same code as principal/teacher)
    Pa->>G: login phone OTP (users/{uid}.roles = [])
    Pa->>G: pick "I am a parent" (intent picker, P4.3.0)
    Pa->>G: paste school inviteCode
    G->>FN: joinSchoolAsParent(inviteCode, displayName)
    FN->>FS: validate inviteCode -> school exists
    FN->>FS: schools/{schoolId}/parents/{parentId}.userId=caller.uid, joinedAt
    FN->>FS: users/{parentUid}.roles += "parent"
    FN->>FS: users/{parentUid}.schoolIds += schoolId
    FS-->>G: onSnapshot fires -> parent home unlocked instantly
    Pa->>G: pair with child via pairing code (existing v1 flow)
  end

  rect rgb(225, 240, 245)
    Note over Pa,FS: Every later session (no code)
    Pa->>G: login phone OTP
    G->>FS: read users/{uid} -> roles = ["parent"]
    G-->>Pa: route directly to ParentNavigator
  end
```

**Edge cases:**
- **Wrong code.** `joinSchoolAsParent` returns `invalid-argument` with a friendly message; nothing is written, retries are free.
- **Re-submitted same code.** Idempotent — if `users/{uid}.roles` already includes `'parent'` AND `schoolIds` already contains the school, the callable returns success without writing anything.
- **Parent joins second school later.** Allowed — the callable array-unions the second `schoolId` into `users/{uid}.schoolIds`. The parent role is already present so `roles[]` doesn't change.

### 6.4 Student (ZKid)

**Manual hand-off model.** The parent hands the **same school `inviteCode`** (received from the principal in §6.3) to the child along with the grade + section. No automated SMS; the parent enters or dictates the code to the child as part of setting up the kid's device.

**One-time code, sticky role, NO approval gate.** The child enters the code + grade + section **exactly once** during first-time ZKid signup. The `joinSchool` callable validates the code, picks the matching class, links the child to the class roster, AND grants `roles: ['child']` server-side in a single transaction. **No principal/admin approval** — the principal can audit the roster but doesn't approve each child. After the one-time entry, the phone is permanently bound to the child role; every later OTP login skips the school-code screen and lands directly on the ZKid home.

```mermaid
sequenceDiagram
  participant Pa as Parent
  participant K as ZKid
  participant FN as Functions
  participant FS as Firestore

  rect rgb(245, 240, 225)
    Note over Pa,K: First-time signup (one-shot)
    Pa-->>K: share school inviteCode + grade + section MANUALLY
    K->>K: phone OTP (users/{uid}.roles = [])
    K->>K: enter pairing code from parent
    K->>FN: bindToParent(pairingCode)
    FN->>FS: create children/{childUid}, link parentUid
    K->>K: enter school inviteCode + grade + section
    K->>FN: joinSchool(inviteCode, grade, section)
    FN->>FS: validate inviteCode -> school + class found
    FN->>FS: children/{childUid}.classId = {schoolId, classId}
    FN->>FS: schools/{schoolId}/classes/{classId}.studentChildUids += childUid
    FN->>FS: users/{childUid}.roles += "child"
    FN->>FS: users/{childUid}.schoolIds += schoolId
    K->>K: onboarding wizard (location, accessibility, etc.)
  end

  rect rgb(225, 240, 245)
    Note over K,FS: Every later session (no code)
    K->>K: phone OTP
    K->>FS: read users/{uid} -> roles = ["child"]
    K-->>K: route directly to ZKid home (no code, no pairing, no school step)
  end
```

**Edge cases:**
- **Wrong code or grade/section mismatch.** `joinSchool` returns `invalid-argument`; child stays on the same screen with an inline error.
- **Class not yet created.** If the principal has the school but not the matching grade/section class yet, callable returns `failed-precondition` ("ask your school to add Class {grade}{section}"). The child can retry once the principal creates it.
- **Child without phone (rare).** The pairing-only fallback from v1 still works: parent creates `children/{uid}` without an auth user. In that case there is no `users/{uid}` doc with `roles[]`; the child is identified purely via the `children/{uid}` doc. Role-gating in ZKid uses `children/{uid}` presence as a fallback signal when `users/{uid}.roles` is absent.

## 7) Payment & Subscriptions (Deferred)

Payment and subscription plumbing is **not in the current build scope**. Build the full product end-to-end first (schools, teachers, child study loop, curated lessons, quizzes, reports), then add monetization.

When implemented later, the planned approach (for reference only):

- **Provider:** Razorpay (India — UPI, cards, school B2B + parent B2C recurring)
- **Plans:** `school_basic`, `school_premium`, `parent_premium`
- **Server-only writes:** `subscriptions/`, `paymentEvents/`, `invoices/` — only Cloud Functions mutate
- **Gating:** education features read-only when subscription lapses; KidSafe core stays free

Do **not** add `packages/shared-payments/`, Razorpay SDK, billing routes, or webhook handlers until a dedicated post-MVP payment phase.

## 8) Updated Firestore Schema (Education)

Unchanged collections from v1: `users`, `children`, `apps`, `events`, `usageDaily`.

New collections summary:

```text
schools/{schoolId}
  ├─ classes/{classId}
  │   └─ subjects/{subjectId}
  │       └─ chapters/{chapterId}
  │           └─ topics/{topicId}
  └─ teachers/{teacherId}

curriculum/{curriculumId}
  chapters/{chapterId}
    topics/{topicId}              # full curated content + quiz (see §8.3)

studyAssignments/{assignmentId}
quizAttempts/{attemptId}
rewardCatalog/{rewardId}
```

**Source of truth:** content team prepares JSON offline. Engineering **imports** it — no OpenAI/Gemini for lessons in MVP.

```json
    {
      "question": "How does a solid turn into a liquid?",
      "answer": "When heat is added, particles move faster and break free from fixed positions — this is melting.",
      "videoUrl": "https://youtube.com/watch?v=approved_brainstorm"
    }
  ],
  "quiz": [
    {
      "questionId": "q1",
      "type": "mcq",
      "question": "Force is a:",
      "options": ["color", "push or pull", "sound", "temperature"],
      "correctIndex": 1,

  "status": "published",
  "curatedBy": "content_team",

```

Field guide:

| Field | Purpose |
|---|---|
| `explanation` | Main lesson text child reads first |
| `examples` | Real-life examples (array of strings) |
| `videoUrl` | Intro/explanation YouTube link (approved) |
| `brainstorming[]` | Common gaps students miss — each has question, answer, videoUrl |
| `quiz[]` | MCQs bundled with topic; server scores against this |
| `status` | `draft` → `published` (only published topics assignable) |



## 8.4 Feature Interaction Map

This section answers: **"when X happens, what else fires?"**

Use it together with the function inventory (§9) to understand any code path end-to-end.

### 8.4.1 Setup chain (one-time per school)

```mermaid
sequenceDiagram
  participant Admin as Zerebro Admin
  participant Principal as Zerebro Campus
  participant Teacher as ZConnect (teacher mode)
  participant Parent as ZConnect (parent mode)
  participant Child as ZKid
  participant FN as Cloud Functions
  participant FS as Firestore

  Admin->>FS: create schools/{schoolId} (with auto-generated inviteCode)
  Admin-->>Principal: share inviteCode MANUALLY (SMS/WhatsApp/in-person)
  Principal->>FN: claimSchool(inviteCode, displayName)
  FN->>FS: schools/{id}/principals/{principalId}.status="pending"
  Admin->>FN: approvePrincipal(schoolId, principalId)
  FN->>FS: principals/{principalId}.status="active"
  FN->>FS: schools/{id}.principalUid = userId
  FN->>FS: users/{principalUid}.roles += "principal"
  Principal->>FS: create classes/{classId} + subjects (with curriculumId)
  Principal->>FN: rotateTeacherCode()
  FN->>FS: schools/{id}.teacherCode = NEW
  Principal-->>Teacher: share teacher code
  Teacher->>FN: requestTeacherJoin(code, displayName)
  FN->>FS: teachers/{teacherId}.status = "pending"
  Principal->>FN: approveTeacher(teacherId)
  FN->>FS: teachers/{teacherId}.status = "active"
  FN->>FS: users/{teacherUid}.roles += "teacher"
  Principal-->>Parent: re-share school inviteCode MANUALLY (same code)
  Parent->>FN: joinSchoolAsParent(inviteCode, displayName)
  FN->>FS: schools/{schoolId}/parents/{parentId}.userId = caller.uid
  FN->>FS: users/{parentUid}.roles += "parent"
  FN->>FS: users/{parentUid}.schoolIds += schoolId
  Parent->>FS: pair child (existing v1 flow)
  Parent-->>Child: re-share school inviteCode + grade + section MANUALLY
  Child->>FN: joinSchool(inviteCode, grade, section)
  FN->>FS: children/{uid}.classId = {schoolId, classId}
  FN->>FS: classes/{classId}.studentChildUids += childUid
  FN->>FS: users/{childUid}.roles += "child"
  FN->>FS: users/{childUid}.schoolIds += schoolId
```

**Side effects:**
- `users/{teacherUid}.roles += "teacher"` → ZConnect role switcher reflects new role on next snapshot
- `classes/{classId}.studentChildUids[]` → principal class roster updates
- `children/{uid}.classId` → ZKid Study Mission listener starts filtering by this classId

**Important — every code is one-time only and every hand-off is MANUAL.** All four hand-offs in the chain are manual (WhatsApp / SMS / in-person — there is no automated SMS callable on our side):
- `Admin-->>Principal: share inviteCode` (consumed by `claimSchool` → admin verifies → `roles += "principal"`)
- `Principal-->>Teacher: share teacher code` (consumed by `requestTeacherJoin` → principal verifies → `roles += "teacher"`)
- `Principal-->>Parent: re-share school inviteCode` (consumed by `joinSchoolAsParent` → **NO approval gate** → `roles += "parent"` immediately if code is valid)
- `Parent-->>Child: re-share school inviteCode + grade + section` (consumed by `joinSchool` → **NO approval gate** → `roles += "child"` immediately if code + class match)

Each user submits their code **exactly once**, at first-time signup. After the role is written to `users/{uid}.roles`, the phone number is permanently bound to that role; every later OTP login resolves to the same Firebase UID, reads the same `roles[]`, and skips the code-entry screen entirely.

**Why principal & teacher have an approval gate but parent & child don't.** Principal and teacher get **broad cross-user access** (a principal can rotate teacher codes / approve teachers / read all class reports for the school; a teacher can assign topics to a whole class). Parent and child only get **access to their own data** (parent: their own paired children; child: their own assignments). A leaked or mis-distributed school `inviteCode` cannot escalate someone into more than parent/child of their own data, so an approval queue would be ceremony without security benefit.

### 8.4.2 Daily learning loop

```mermaid
sequenceDiagram
  participant Teacher as ZConnect (teacher)
  participant FN as Cloud Functions
  participant FS as Firestore
  participant Child as ZKid
  participant Parent as ZConnect (parent)

  Teacher->>FN: assignTopic(classId, subjectId, chapterId, topicId)
  FN->>FS: studyAssignments/{id} created
  Note over FS: Snapshot fires
  FS-->>Child: ZKid Study Mission shows new card
  FS-->>Teacher: Teacher home updates assignments list

  Child->>FS: read curriculum/.../topics/{topicId}
  Note over Child: renders explanation + examples + video + brainstorming + quiz

  Child->>FN: submitQuizAttempt(assignmentId, answers)
  FN->>FS: read topic.quiz to validate
  FN->>FS: quizAttempts/{id} written with server score
  Note over FS: Trigger fires
  FS->>FN: onQuizAttemptWrite (trigger)
  FN->>FS: pick eligible rewardCatalog entry
  FN->>FS: rewardUnlocks/{id} written

  FS-->>Child: ZKid reward screen
  FS-->>Parent: Parent Study tab shows score + reward
  FS-->>Teacher: Teacher class report updates
```

**Side effects:**
- Creating one `studyAssignments` doc updates 2 UIs (ZKid + teacher).
- Creating one `quizAttempts` doc triggers reward creation AND updates 3 UIs (ZKid, parent, teacher).
- All updates are real-time via Firestore snapshots — no polling.

### 8.4.3 Nightly aggregation (principal dashboards)

```mermaid
sequenceDiagram
  participant Cron as Cloud Scheduler
  participant FN as aggregateClassReports
  participant FS as Firestore
  participant Principal as Zerebro Campus

  Cron->>FN: trigger at 02:00 IST
  FN->>FS: query quizAttempts (last 24h, group by classId)
  FN->>FS: classReports/{classId}/daily/{date} written
  FN->>FS: mark topics weak if class avg < 60%
  Principal->>FS: dashboard reads pre-computed classReports
  FS-->>Principal: fast load (< 1s)
```

**Why pre-compute?** Live aggregation of thousands of `quizAttempts` on every dashboard load would be slow and expensive. Cron writes summaries once a night → dashboards read tiny `classReports` docs.

### 8.4.4 Cross-feature interaction matrix

What writing to one collection affects elsewhere:

| Write | Triggers / Affects |
|---|---|
| `studyAssignments/{id}` (create) | ZKid Study Mission (snapshot); teacher home list (snapshot) |
| `quizAttempts/{id}` (create) | `onQuizAttemptWrite` trigger → `rewardUnlocks/{id}`; parent Study tab; teacher class report; nightly `aggregateClassReports` |
| `rewardUnlocks/{id}` (create) | ZKid reward screen; parent Study tab (reward chip) |
| `users/{uid}.roles += 'teacher'` | ZConnect role switcher appears on next render; teacher's future OTP logins skip the code-entry screen entirely (role is sticky on the phone number) |
| `users/{uid}.roles += 'principal'` | Zerebro Campus dashboard unlocks on next snapshot; principal's future OTP logins skip the school-code claim screen entirely (role is sticky on the phone number) |
| `schools/{id}/principals/{principalId}.status = 'active'` | Mirrors with `schools/{id}.principalUid = userId` (denormalized pointer for fast lookups); pending-state UI in Campus flips to dashboard |
| `users/{uid}.roles += 'parent'` | ZConnect routes the user directly to ParentNavigator; parent's future OTP logins skip the school-code screen entirely (role is sticky on the phone number). No approval required — granted by `joinSchoolAsParent` the instant the code validates. |
| `users/{uid}.roles += 'child'` | ZKid routes the user directly to ZKid home; child's future OTP logins skip the school-code + grade/section screen entirely. No approval required — granted by `joinSchool` the instant the code + class lookup validates. |
| `users/{uid}.schoolIds += schoolId` | Used by principal-side queries (parent roster, child roster) and by ZConnect/ZKid to know which school's announcements/reports to subscribe to. |
| `children/{uid}.classId` set | ZKid Study Mission listener registers correct class filter; class roster updates for teacher + principal |
| `schools/{id}.teacherCode` rotated | Old code becomes invalid for `requestTeacherJoin` |
| `curriculum/.../topics/{id}` written by import | Becomes assignable in teacher's "Assign Topic" picker (status filter: `published`) |
| `rewardCatalog/{id}` created | Eligible for `onQuizAttemptWrite` reward picker on next quiz pass |

### 8.4.5 What does NOT trigger anything

For clarity:

| Write | No side effect |
|---|---|
| `children/{uid}.currentLocation` | Parent map updates, but no education feature reads this |
| `apps/{pkg}.isBlocked` | KidSafe enforcement only; not part of education chain |
| `usageDaily/*` | Parent screen-time UI only |
| Pure principal CRUD on `classes/*` (renaming etc.) | Subscribed UIs update; no callable/trigger fires |

This separation keeps the education stack independent of the KidSafe-core stack — either can break without taking down the other.

## 13) Risks & Safeguards

| Risk | Mitigation |
|---|---|
| Metro + monorepo path issues | Standard `watchFolders` + `nodeModulesPaths` + `disableHierarchicalLookup` config; `node-linker=hoisted` |
| Native module path break after extraction | Keep Gradle module names identical to v1, just relocate the source root |
| Wrong curated quiz answer | Content team QA + import validator + spot-check before `published` status |
| Unsafe reward link | Strict allowlist in `rewardCatalog`, admin moderation only |
| Multi-role user confusion | Single role switcher UI, `primaryRole` default, audit logging on switch |
| Cross-app data leak | Firestore rules strictly check role + school binding; ZKid refuses parent-shaped reads |
| Child app reverse-engineered | ZKid APK doesn't bundle parent UI; secrets are server-side only |
